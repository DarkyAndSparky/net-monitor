## Пентест-аудит — найдено и исправлено

Реальные атаки через живой сервер (не просто чтение кода) — access control, SSRF, file upload,
timing attacks, information disclosure.

- [x] **Broken access control** — проверено: viewer/operator не может повысить себе роль, не может
  выполнять admin/operator-действия напрямую через API в обход UI. 10/10 реальных попыток
  privilege escalation отбиты корректно (403). Уязвимостей не найдено.
- [x] **SSRF через настраиваемые webhook/ntfy URL** — не было никакой защиты: любой admin/operator
  мог указать `169.254.169.254` (cloud-metadata, кража IAM-credentials) или `gopher://`/`file://`
  схему. Добавлен `src/services/urlGuard.js` — точечная защита (блокирует только link-local диапазон
  и не-http(s) схемы), сознательно **не** блокирует приватные LAN-адреса (10.x/172.16.x/192.168.x) —
  это self-hosted инструмент, слать webhook на внутренний сервер в своей сети легитимно
- [x] **SVG XSS через логотип** — старый blacklist-фильтр (`<script`, `onXXX=`) обходился четырьмя
  независимыми способами: `javascript:` в `xlink:href`, SMIL-анимация (`<animate>`), `<foreignObject>`,
  вложенный `data:text/html`. Impact шире, чем казалось: логотип отдаётся `GET /api/branding/logo`
  **без авторизации** — исполнился бы у любого посетителя страницы логина, не только у admin.
  Фильтр расширен, все 4 вектора протестированы и заблокированы, легитимные логотипы не задеты
- [x] **Timing-based user enumeration** — для несуществующего username (или LDAP выключен) сервер
  возвращал 401 почти мгновенно, а для существующего — после дорогого `scrypt` (~50мс). Разница
  измерима статистически, выдаёт какие логины существуют. Добавлен constant-time padding
  (`timingPad()`) — реальный замер на сервере: разница упала до <1мс
- [x] **Information disclosure** — не было ни explicit error handler (при NODE_ENV, отличном от
  `production`, который нигде не форсируется явно, дефолтный Express-обработчик отдаёт полный stack
  trace), ни явного 404 для `/api/*` (дефолтная HTML-страница Express светит версию фреймворка в
  разметке). Добавлен global error handler (логирует полностью на сервере, клиенту — только
  `internal_error`) и JSON 404. Заодно отключён заголовок `X-Powered-By`
- [x] **Prototype pollution** — проверено: нигде не используется `Object.assign(target, userInput)`
  или `for...in` по пользовательским данным. Весь проект последовательно использует explicit-whitelist
  паттерн для настроек — защищает от этого класса атак как побочный эффект
- [x] **Rate limiting coverage** — проверено: применяется глобально ко всем `/api/*`, `/login`
  защищён двойно (общий write-лимитер + свой per-IP lockout 5 попыток/5 мин)
- [x] **npm audit** — 0 известных CVE во всём дереве зависимостей
- [x] **Права доступа на файл БД** — `.db`/`.db-wal`/`.db-shm` создавались с правами `644`
  (world-readable), хотя внутри — password-хеши, LDAP/SMTP-пароли, Telegram bot token в открытом
  виде (маскировка `••••••••` — только в API-ответе, не в самой БД). Любой пользователь системы
  мог их прочитать. Исправлено: `process.umask(0o077)` (защищает и WAL/SHM, создаваемые SQLite
  позже) + явный `chmod 600` на существующий файл (для апгрейда старых инсталляций)
- [x] **Отсутствие глобального перехватчика ошибок** — самая серьёзная находка раунда: без
  `unhandledRejection`/`uncaughtException` handler'ов одно необработанное исключение в ЛЮБОМ из
  ~50 async route-хендлеров роняло бы **весь процесс** (дефолтное поведение Node 15+), а не один
  запрос — простой сервиса для всех подключённых пользователей разом. Подтверждено реальным тестом:
  временный роут с намеренным `TypeError` без `try/catch` — до фикса уронил бы сервер, после —
  процесс жив, лог содержит ошибку, следующий запрос обслуживается нормально

## Критичные баги, найденные и исправленные за эту сессию

Помимо новых фич, два прогона глубокого аудита (функциональный + security) нашли и закрыли реальные проблемы:

- **Зависание сервера** — `POST /api/login` с пустыми учётными данными вешал соединение без ответа (необработанное исключение `node:sqlite`, не перехватываемое Express 4 в async-роуте)
- **Молчаливая потеря настроек** — роуты `/api/categories` и `/api/sites` были физически недостижимы из-за неверной точки монтирования роутера; вкладка «Категории» не сохраняла изменения
- **Потеря данных при восстановлении бэкапа** — площадки, привязка устройств к ним, SNMP-индекс интерфейса трафика, настройки LDAP и webhook-событий не восстанавливались из `backup/restore`
- **Сброс настроек трафика** — `POST /api/features` сбрасывал флаг мониторинга трафика при сохранении любой другой настройки
- **XSS** в непроявленной ранее вкладке логов — значения полей лога вставлялись в DOM без экранирования
- **Нерабочая кнопка** смены пароля при первом входе — `ReferenceError` на несуществующей функции (та же причина ломала генерацию токена агента и кнопку «Проверить сейчас»)
- Ряд проблем установочных Windows/Linux-скриптов: ложные ошибки при опциональной нативной сборке, обрыв после установки зависимостей, гонка при открытии браузера, кракозябры без UTF-8
- Замена `ldapjs` (decommissioned, без патчей безопасности с мая 2024) на активно поддерживаемый `ldapts`

Полный список — в `CHANGELOG.md`.
