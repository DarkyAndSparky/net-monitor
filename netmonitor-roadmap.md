## Расширение тестового покрытия

Замер `c8` поверх текущих 53 тестов: **57.3% statements / 43.2% functions** в среднем —
но эта цифра усредняет только 8 из 22 файлов `src/`, которых тесты вообще касаются.
**14 файлов — 0% покрытия**, целиком нетронуты тестами. Ниже — план по приоритету.

### 🔴 Критично — HTTP-роуты вообще без тестов
Самая рискованная зона: именно тут пентест-аудит (раздел ниже) нашёл реальные уязвимости
(timing attack, SSRF, XSS), а регресс здесь никакой тест не поймает.

- [x] `src/routes/auth.js` — было 0%, теперь **86.6%**. Добавлен
  `test/integration/auth.test.js` (18 тестов): неверный/несуществующий username через
  `timingPad()`-ветку, lockout после 5 попыток + блокировка даже с верным паролем,
  `/api/me`, весь `change-password` (слабый пароль/неверный текущий/совпадение со
  старым), создание пользователей (невалидный username, дубликат, фоллбек неизвестной
  роли на viewer), защита последнего админа (понижение роли и удаление), `requireAdmin`
  на `/api/users`, `logout`
- [x] `src/middleware/rate-limit.js` — было 0%, теперь **100%**. Добавлен
  `test/unit/rate-limit.test.js` (7 тестов) на отдельном мини-express-приложении:
  все 4 профиля (read 300/мин, write 60/мин, scan 10/5мин, agent 20/мин по токену),
  skip для `/api/health` и `/api/events`, стандартные `RateLimit-*` заголовки (legacy
  выключены), изоляция лимита `agentLimiter` по токену, а не по IP, и отдельно —
  `RATE_LIMIT_DISABLED=true` действительно превращает лимитер в passthrough

**Побочная находка при внедрении, важнее самих тестов**: у `server.js` не было
обработчика `SIGTERM`/`SIGINT` вообще — сигнал убивал процесс мгновенно, без единого
шанса закрыть слушающие сокеты или соединение с БД. В проде именно `SIGTERM` шлют
systemd (`systemctl stop`), Docker (`docker stop`) и k8s при остановке пода — то есть
штатная остановка сервиса вела себя как аварийный краш. Заметно это стало из-за
тестовой инфраструктуры: интеграционные тесты убивали спавненный сервер через
`SIGKILL`, из-за чего V8 не успевал сбросить coverage на диск, и весь HTTP-слой
(`settings.js`, `monitoring.js`, `integrations.js`, `discovery.js` и т.д.) в отчётах
выглядел как «файл не тронут тестами вообще», хотя часть кода реально исполнялась —
просто измерить это было нечем. Добавлен `gracefulShutdown()` в `server.js` (закрывает
слушающие сокеты, потом БД, форс-выход через 10 сек, если что-то держит сокет), тесты
переведены на `SIGTERM` + ожидание `exit` вместо `SIGKILL`. Итог: реальное покрытие
всплыло сразу по всем файлам HTTP-слоя (`settings.js` 76%, `monitoring.js` 66%,
`integrations.js` 34% и т.д. — раньше их не было видно в отчёте вообще), а сам продакшн
получил рабочий graceful shutdown, которого не было.
- [x] `src/routes/discovery.js` — было 0% (маскировано, реально не тронуто до фикса
  shutdown), теперь **51.8%**. Добавлен `test/integration/discovery.test.js`
  (19 тестов): `local-subnets`, валидация `scan` (invalid_cidr/range_too_big — реальный
  ping-sweep НЕ тестируется, в песочнице нет ICMP и он виснет), `add-bulk` (создание +
  пропуск дубликатов/пустых записей), CRUD ручных связей топологии, валидация

- [x] `src/routes/maintenance.js` — было 46%, теперь **86.2%**. Добавлен

### 🟠 Важно — покрыть регрессии на уже найденные критичные баги
Каждый из багов в разделе «Критичные баги, найденные и исправленные» ниже был найден
ручным аудитом, не тестом — то есть ни один из них не защищён от повторного появления.
Конкретные регресс-тесты, которых пока нет:
- [ ] `POST /api/login` с пустыми `{}` учётными данными не должен вешать соединение

- [ ] Backup/restore round-trip: создать площадку + привязать устройство + настроить

- [ ] Значения полей лога рендерятся в DOM экранированными (XSS во вкладке логов) —
  это, строго говоря, фронтенд-тест (нужен Playwright, см. ниже), но пока можно

## Пентест-аудит — найдено и исправлено

Реальные атаки через живой сервер (не просто чтение кода) — access control, SSRF, file upload,
timing attacks, information disclosure.

- [x] **Broken access control** — проверено: viewer/operator не может повысить себе роль, не может
  выполнять admin/operator-действия напрямую через API в обход UI. 10/10 реальных попыток
  privilege escalation отбиты корректно (403). Уязвимостей не найдено.
- [x] **SSRF через настраиваемые webhook/ntfy URL** — не было никакой защиты: любой admin/operator
  мог указать `169.254.169.254` (cloud-metadata, кража IAM-credentials) или `gopher://`/`file://`
  схему. Добавлен `src/services/urlGuard.js` — точечная защита (блокирует только link-local диапазон
  и не-http(s) схемы), сознательно **не** блокирует приватные LAN-адреса (10.x/172.16.x/192.168.x) —
  это self-hosted инструмент, слать webhook на внутренний сервер в своей сети легитимно
- [x] **SVG XSS через логотип** — старый blacklist-фильтр (`<script`, `onXXX=`) обходился четырьмя
  независимыми способами: `javascript:` в `xlink:href`, SMIL-анимация (`<animate>`), `<foreignObject>`,
  вложенный `data:text/html`. Impact шире, чем казалось: логотип отдаётся `GET /api/branding/logo`
  **без авторизации** — исполнился бы у любого посетителя страницы логина, не только у admin.
  Фильтр расширен, все 4 вектора протестированы и заблокированы, легитимные логотипы не задеты
- [x] **Timing-based user enumeration** — для несуществующего username (или LDAP выключен) сервер
  возвращал 401 почти мгновенно, а для существующего — после дорогого `scrypt` (~50мс). Разница
  измерима статистически, выдаёт какие логины существуют. Добавлен constant-time padding
  (`timingPad()`) — реальный замер на сервере: разница упала до <1мс
- [x] **Information disclosure** — не было ни explicit error handler (при NODE_ENV, отличном от
  `production`, который нигде не форсируется явно, дефолтный Express-обработчик отдаёт полный stack
  trace), ни явного 404 для `/api/*` (дефолтная HTML-страница Express светит версию фреймворка в
  разметке). Добавлен global error handler (логирует полностью на сервере, клиенту — только
  `internal_error`) и JSON 404. Заодно отключён заголовок `X-Powered-By`
- [x] **Prototype pollution** — проверено: нигде не используется `Object.assign(target, userInput)`
  или `for...in` по пользовательским данным. Весь проект последовательно использует explicit-whitelist
  паттерн для настроек — защищает от этого класса атак как побочный эффект
- [x] **Rate limiting coverage** — проверено: применяется глобально ко всем `/api/*`, `/login`
  защищён двойно (общий write-лимитер + свой per-IP lockout 5 попыток/5 мин)
- [x] **npm audit** — 0 известных CVE во всём дереве зависимостей
- [x] **Права доступа на файл БД** — `.db`/`.db-wal`/`.db-shm` создавались с правами `644`
  (world-readable), хотя внутри — password-хеши, LDAP/SMTP-пароли, Telegram bot token в открытом
  виде (маскировка `••••••••` — только в API-ответе, не в самой БД). Любой пользователь системы
  мог их прочитать. Исправлено: `process.umask(0o077)` (защищает и WAL/SHM, создаваемые SQLite
  позже) + явный `chmod 600` на существующий файл (для апгрейда старых инсталляций)
- [x] **Отсутствие глобального перехватчика ошибок** — самая серьёзная находка раунда: без
  `unhandledRejection`/`uncaughtException` handler'ов одно необработанное исключение в ЛЮБОМ из
  ~50 async route-хендлеров роняло бы **весь процесс** (дефолтное поведение Node 15+), а не один
  запрос — простой сервиса для всех подключённых пользователей разом. Подтверждено реальным тестом:
  временный роут с намеренным `TypeError` без `try/catch` — до фикса уронил бы сервер, после —
  процесс жив, лог содержит ошибку, следующий запрос обслуживается нормально

## Критичные баги, найденные и исправленные за эту сессию

Помимо новых фич, два прогона глубокого аудита (функциональный + security) нашли и закрыли реальные проблемы:

- **Зависание сервера** — `POST /api/login` с пустыми учётными данными вешал соединение без ответа (необработанное исключение `node:sqlite`, не перехватываемое Express 4 в async-роуте)
- **Молчаливая потеря настроек** — роуты `/api/categories` и `/api/sites` были физически недостижимы из-за неверной точки монтирования роутера; вкладка «Категории» не сохраняла изменения
- **Потеря данных при восстановлении бэкапа** — площадки, привязка устройств к ним, SNMP-индекс интерфейса трафика, настройки LDAP и webhook-событий не восстанавливались из `backup/restore`
- **Сброс настроек трафика** — `POST /api/features` сбрасывал флаг мониторинга трафика при сохранении любой другой настройки
- **XSS** в непроявленной ранее вкладке логов — значения полей лога вставлялись в DOM без экранирования
- **Нерабочая кнопка** смены пароля при первом входе — `ReferenceError` на несуществующей функции (та же причина ломала генерацию токена агента и кнопку «Проверить сейчас»)
- Ряд проблем установочных Windows/Linux-скриптов: ложные ошибки при опциональной нативной сборке, обрыв после установки зависимостей, гонка при открытии браузера, кракозябры без UTF-8
- Замена `ldapjs` (decommissioned, без патчей безопасности с мая 2024) на активно поддерживаемый `ldapts`

Полный список — в `CHANGELOG.md`.

### Найдено при написании тестов на discovery.js (эта сессия)

- **SQLite трактует `""` как имя колонки, а не строку** — 6 SQL-запросов дедупликации
  устройств по MAC/IP использовали `mac!=""` / `ip!=""` (двойные кавычки). SQLite
  парсит двойные кавычки как идентификатор (имя колонки), не как строковый литерал —
  такой идентификатор не существует, и запрос падает с `no such column: ""`.
  Правильно: одинарные кавычки, `mac!=''`. Затронуты и **всегда падали 500**:
  `POST /api/discovery/add-bulk`, проверка «уже известных» IP в `/api/discovery/scan`,
  автопостроение топологии через MikroTik-SNMP (`discovery.js`), а также дедуп при
  импорте устройств с MikroTik/UniFi/Cisco (`integrations.js`, 3 места). Исправлено во
  всех 6 местах. Не всплывало раньше именно потому, что этих функций не касался ни один
  тест — нашлось только когда `add-bulk` реально прогнали через тест.
- **Маскировка проверки роли гейтом смены пароля** — свежесозданный пользователь
  получает `mustChangePassword=true`, и до смены пароля ЛЮБОЙ роут отвечает `403
  password_change_required`, включая роуты, которые тест хотел проверить на `403
  forbidden` (нехватка роли). В нескольких уже написанных тестах (`auth.test.js`,
  `agent.test.js`, `integrations.test.js`) статус совпадал (403) по случайной причине,
  а не по факту проверки роли — исправлено добавлением смены пароля перед такими
  проверками и явным assert на код ошибки (`forbidden`, не `password_change_required`).
