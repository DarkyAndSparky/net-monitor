Docs / Установка

Установка

Ручная установка на Windows или Linux/macOS без Docker.

Windows (install.bat)

Запустите install.bat от имени Администратора — скрипт установит зависимости npm и сгенерирует TLS-сертификат.

install.bat        # от имени Администратора!
✓ Нативных модулей нет. SQLite использует встроенный node:sqlite (Node.js >= 22.5.0) — Python, Build Tools и node-gyp не нужны. Просто npm install.

Ручной запуск (если скрипт не устраивает)

npm install
node server.js

Linux / macOS (install.sh)

chmod +x install.sh
./install.sh

Скрипт определяет пакетный менеджер (apt / yum / brew) и устанавливает build-зависимости (python3 make g++) автоматически.

Первый запуск

При первом старте автоматически создаётся:

ЧтоГдеПримечание
БДdata/netmonitor.dbSQLite WAL, схема + дефолтные категории
Пользовательadmin / admin0000Смена пароля обязательна при первом входе — сервер не пустит дальше без неё
Секрет сессииdata/.session-secretГенерируется один раз, не трогать
TLS-сертификатdata/certs/Самоподписанный, генерируется make-cert.bat/.sh
✓ Сервер запущен: откройте https://localhost:9222. Браузер покажет предупреждение о самоподписанном сертификате — нажмите «Дополнительно» → «Перейти на сайт».

Docs / Docker-деплой

Docker-деплой

Рекомендуемый способ для продакшн-серверов на Linux.

Быстрый старт

git clone https://github.com/DarkyAndSparky/net-monitor.git
cd net-monitor
docker compose up -d

Сервис поднимается на порту 9222. Данные хранятся в ./data (volume).

network_mode: host — используется чтобы контейнер мог пинговать устройства локальной сети. На Windows Docker Desktop это не работает — Docker-образ предназначен для деплоя на Linux-сервер.

docker-compose.yml

services:
  net-monitor:
    build: .
    container_name: net-monitor
    restart: unless-stopped
    ports:
      - "9222:9222"
    volumes:
      - ./data:/app/data
    network_mode: host   # нужен для ping в локальной сети
    cap_add:
      - NET_RAW          # разрешает ping
      - NET_ADMIN        # разрешает ARP

Сборка образа

docker build -t net-monitor .
docker run -d --name net-monitor --network host   -v $(pwd)/data:/app/data   --cap-add NET_RAW --cap-add NET_ADMIN   net-monitor

Обновление

git pull
docker compose build --no-cache
docker compose up -d
Данные сохраняются — volume ./data не пересоздаётся при обновлении контейнера.

Переменные окружения в Docker

environment:
  - PORT=9222
  - METRICS_TOKEN=мой_секрет
  - HTTP_REDIRECT_PORT=0   # отключить редирект если не нужен
Docs / Настройка

Настройка системы

Все настройки хранятся в SQLite таблице settings и меняются через UI или API.

Фиче-флаги

Раздел Настройки → Функции. Все дополнительные модули выключены по умолчанию.

ФлагЧто включает
snmpSNMP-опрос устройств (OID, аптайм, CPU MikroTik)
portChecksПроверка TCP-портов сервисов
incidentsЖурнал инцидентов + эскалация алертов
auditLogАудит-лог всех действий пользователей

Интервалы мониторинга

Глобальный интервал по умолчанию — 60 сек. Минимальный интервал — 10 сек. Задаётся индивидуально для каждого устройства в его карточке → поле «Интервал проверки».

⚠ При большом числе устройств (N) и малом интервале (I) у сервера будет N/I одновременных ping-запросов. Для 500 устройств с интервалом 30 сек — ~17 пингов в секунду. Планировщик запускает новый тик каждые 5 сек и конкурентно не перегружает сеть, но учитывайте нагрузку на систему.

TLS / HTTPS

Если файлы data/certs/cert.pem и data/certs/key.pem существуют — сервер автоматически запускается по HTTPS. Для генерации самоподписанного сертификата:

make-cert.bat    # Windows
bash make-cert.sh  # Linux/macOS

Для использования своего сертификата (Let's Encrypt и т.д.) — укажите пути через переменные окружения TLS_CERT_FILE и TLS_KEY_FILE.

Docs / Бэкап и восстановление

Бэкап и восстановление

Через UI

Настройки → Резервная копия → кнопка «Скачать бэкап». Скачивается JSON-файл с полным дампом: устройства, категории, топология, настройки, инциденты, аудит (последние 5000 записей).

⚠ Восстановление полностью заменяет текущие данные. Перед восстановлением рекомендуется сохранить текущий бэкап.

Через API

# Скачать бэкап
curl -s -b cookies.txt https://localhost:9222/api/backup -o backup.json

# Восстановить
curl -s -b cookies.txt -X POST https://localhost:9222/api/backup/restore \
  -H "Content-Type: application/json" --data @backup.json

Прямой бэкап SQLite

Файл data/netmonitor.db — обычный SQLite. Можно копировать напрямую (сервер должен быть остановлен, или использовать sqlite3 .backup).

# Горячая копия (сервер может работать)
sqlite3 data/netmonitor.db ".backup data/netmonitor-backup.db"

Структура JSON-бэкапа

{
  "version": 2,
  "exportedAt": "2026-08-08T...",
  "devices": { "devices": [...], "categories": [...] },
  "users": { "users": [...] },
  "settings": { "mikrotiks": [], "alerting": {}, "features": {}, ... },
  "topology": { "edges": [...] },
  "incidents": { "closed": [...] },
  "audit": { "entries": [...] }
}

Управление пользователями

Настройки → Пользователи. Создание, смена роли, удаление. Нельзя удалить последнего администратора и нельзя удалить самого себя.

Пароль по умолчанию: admin / admin0000. Смена пароля принудительна — сразу после первого входа система покажет экран смены пароля и заблокирует весь остальной интерфейс до его прохождения (защита от «забыл сменить»). Текущий пароль повторно вводить не нужно — валидная сессия уже подтверждает, что он известен. Это же правило действует для любого нового пользователя, созданного администратором.
Docs / LDAP / Active Directory

LDAP / Active Directory

Вход через AD как дополнение к локальным учётным записям, не замена. Настройки → LDAP/AD.

Как работает

  1. Если введённый логин уже существует локально — используется обычная проверка локального пароля, LDAP не задействуется вообще.
  2. Если логина нет локально и LDAP включён — сервис-аккаунт (Bind DN) ищет пользователя в каталоге по userFilter, затем сервер пытается bind под найденным DN с введённым паролем — это и есть проверка пароля.
  3. При успехе роль определяется по группам (memberOf) через настраиваемые правила «группа → роль», проверяемые сверху вниз. Если ни одна группа не совпала — применяется роль по умолчанию.
  4. Учётная запись создаётся в NetMonitor автоматически (авто-провижининг), роль синхронизируется по группам при каждом следующем входе.

Настройка

ПолеОписание
URL сервераldap://host:389 или ldaps://host:636
Bind DN / парольСервисная учётная запись, только для поиска — создайте отдельную в AD специально для NetMonitor
Base DNГде искать пользователей, например OU=Users,DC=example,DC=local
Фильтр поискаПо умолчанию (sAMAccountName={{username}})
Роли по группамСписок правил «DN группы → роль», первое совпадение побеждает
⚠ Пароль LDAP-пользователей нигде не сохраняется в NetMonitor — проверка идёт только через bind к самому LDAP-серверу при каждом входе. Локальную смену пароля (Настройки → Профиль) для LDAP-аккаунтов система не позволит — пароль меняется только в AD.
Docs / Площадки (Multi-site)

Площадки (Multi-site)

Для компаний с несколькими удалёнными филиалами/объектами под одним NetMonitor. Настройки → Площадки.

Как устроено

Площадка — название, цвет, адрес/комментарий. У каждого устройства есть необязательное поле «Площадка» (вкладка «Дополнительно» в форме устройства). На дешборде — переключатель «Все площадки / конкретная», фильтрующий карточки категорий, ключевые устройства, SLA-виджеты и heat map.

Ограничения

Площадку, на которую ссылается хотя бы одно устройство, удалить нельзя — сначала перепривяжите или удалите устройства.

Docs / Просмотр логов

Просмотр системных логов

Настройки → Логи (только для admin). Логи пишет pino, ротация ежедневная, хранится 7 файлов.

Возможности

  • Фильтр по уровню (TRACE…FATAL), дате (текущий или любой из 7 архивных файлов) и свободному текстовому поиску
  • Live-tail — просмотр в реальном времени через SSE, как docker logs -f. Доступен только для текущего активного файла
  • Скачивание файла целиком (raw) и удаление архивных файлов (текущий активный удалить нельзя)

Уровень логирования

HTTP-access-лог (каждый запрос) пишется на уровне debug — по умолчанию (LOG_LEVEL=info) эти строки не сохраняются. Установите переменную окружения LOG_LEVEL=debug при запуске, если нужно видеть каждый HTTP-запрос в логах.

Docs / Rate Limiting

Rate Limiting

Защита всех API-эндпоинтов от перебора и злоупотребления.

Как устроено

Помимо собственной IP-блокировки на /api/login (5 неудачных попыток → блокировка на 5 минут), все остальные /api/* маршруты защищены через express-rate-limit с тремя профилями лимитов в зависимости от типа операции.

ПрофильЛимитПрименяется к
Чтение (GET)300 запросов / минСписок устройств, статус, история, аптайм — то, что UI опрашивает регулярно
Запись (POST/PUT/DELETE/PATCH)60 запросов / минСоздание/изменение/удаление устройств, настроек, пользователей
Тяжёлые операции10 запросов / 5 минPing-sweep, импорт с MikroTik/UniFi/Cisco, автопостроение топологии
Исключения: /api/health и /api/events (SSE-соединение) не лимитируются — health-check должен отвечать всегда, а SSE держит одно долгоживущее соединение, а не поток отдельных запросов.

Ответ при превышении лимита

HTTP 429 Too Many Requests
Content-Type: application/json
RateLimit-Limit: 60
RateLimit-Remaining: 0
RateLimit-Reset: 42

{
  "error": "rate_limited",
  "message": "Слишком много запросов на изменение данных. Подождите минуту."
}

Фронтенд перехватывает 429-ответы автоматически и показывает toast-уведомление с указанием, сколько секунд осталось до сброса лимита.

Настройка

Переменная окруженияПо умолчаниюОписание
RATE_LIMIT_DISABLEDfalsetrue — полностью отключает rate limiting. Использовать только при отладке или в закрытом тестовом окружении
⚠ Лимиты считаются по IP-адресу отправителя. Если NetMonitor стоит за реверс-прокси (nginx, Traefik) без передачи реального IP через X-Forwarded-For, все запросы могут учитываться как приходящие с одного IP (адреса прокси) — тогда лимиты будут срабатывать быстрее для всех пользователей сразу. Настройте trust proxy в Express соответственно вашей конфигурации прокси.

Логирование

Каждое превышение лимита пишется в лог (pino, уровень warn) с IP-адресом, путём и методом запроса — полезно для выявления попыток перебора или неисправного клиента, который зациклился на запросах.

Docs / Интеграции

Интеграции

MikroTik RouterOS API

Настройки → Интеграции → MikroTik. Добавьте роутер (хост, порт 8728, логин/пароль). Доступные операции:

ОперацияЧто делает
Импорт DHCP-leasesТянет список аренд DHCP, добавляет новые устройства, обновляет IP/MAC существующих
ARP-таблицаСписок устройств из ARP-таблицы роутера с указанием интерфейса
MNDP-соседиОбнаружение MikroTik-устройств через neighbor discovery
АвтотопологияСтроит связи на карте из neighbor-таблицы + ARP (вкладка Обнаружение)
Для подключения по TLS укажите порт 8729 и включите галочку «Использовать TLS».

UniFi Controller

Поддерживаются UniFi Network Application и UniFi OS (UDM/UDR). При добавлении включите галочку «UniFi OS» для современных устройств. Импортирует инфраструктуру (UAP, USW, UGW) и клиентов.

Самоподписанный сертификат UniFi — соединение устанавливается с отключённой проверкой сертификата (rejectUnauthorized: false). Используйте только в доверенной сети.

Cisco SSH

Подключается по SSH, выполняет show ip arp и парсит ARP-таблицу. Поддерживаются старые алгоритмы шифрования (IOS 12.x+). Импортированные устройства получают категорию «workstation», тип «DHCP Client».

LLDP/CDP-автотопология (любой вендор, по SNMP)

Настройки → Обнаружение сети → LLDP/CDP-обнаружение. В отличие от автотопологии MikroTik выше, работает с любым сетевым устройством с включённым SNMP-опросом (галочка в карточке устройства), независимо от вендора. Сначала пробуется стандартный LLDP (IEEE 802.1AB), если сосед его не поддерживает — CDP (Cisco). Найденные соседи сопоставляются с существующими устройствами по IP или имени, недостающие — создаются автоматически, связи строятся на карте с меткой вида ether1 → gi0/1.

⚠ Реальные ответы LLDP/CDP заметно отличаются между вендорами (особенно кодировка chassis ID — MAC vs текст). Если после обновления соседи распознаются нечитаемо для конкретного оборудования — пришлите пример вывода snmpwalk, парсинг можно доточить под конкретного вендора.

OUI (производители по MAC)

База производителей скачивается с standards-oui.ieee.org при первом запуске и обновляется раз в 30 дней. Раздел Настройки → OUI → «Обновить сейчас» для принудительного обновления.

Алерты и уведомления

Настройка

Настройки → Алерты. Включите «Алерты активны» и настройте хотя бы один канал доставки.

Telegram Bot

# 1. Создайте бота через @BotFather, получите токен
# 2. Узнайте chat_id: отправьте боту любое сообщение, затем:
curl https://api.telegram.org/bot<TOKEN>/getUpdates
# В ответе найдите "chat":{"id": ...}

Введите токен и chat_id в настройках. Кнопка «Тест» отправит пробное сообщение.

Webhook

POST-запрос на указанный URL с JSON-телом:

{
  "device": { "id": "d-...", "name": "router-01", "ip": "192.168.1.1", "location": "Серверная" },
  "status": "down",          // "down" | "up" | "test"
  "message": "🔴 router-01 недоступно\nIP: 192.168.1.1",
  "time": "2026-08-08T10:00:00.000Z"
}

Email (SMTP)

Отправка через nodemailer. Поддерживает STARTTLS (порт 587, по умолчанию) и TLS с самого начала (порт 465). Для Gmail/Yandex/Mail.ru обычно нужен «пароль приложения», а не обычный пароль от почты. Кнопка «Тест» отправит пробное письмо.

Ntfy.sh

Self-hosted или публичный push через ntfy.sh — укажите сервер, топик и опциональный токен авторизации. Приоритет и цвет уведомления автоматически подстраиваются под статус (down → высокий приоритет, красный; up → обычный, зелёный).

ПараметрОписание

Эскалация (требует модуль «Инциденты»)

Если устройство недоступно дольше N минут — отправляет отдельное сообщение на другой Telegram chat_id (например, дежурному руководителю). Инцидент помечается флагом «escalated».

Алерты на устройство

В карточке каждого устройства есть галочка «Алерты». Снимите её чтобы исключить конкретное устройство из системы уведомлений, оставив его под мониторингом.

Webhook на любое событие (отдельно от алертов)

Настройки → Webhook-события. В отличие от алертов выше (только недоступность/восстановление устройств), сюда попадает любое действие в системе — создание/удаление устройств, изменение пользователей, импорт, смена настроек и т.д.: тот же набор событий, что пишется в аудит-лог. Работает независимо от того, включён ли сам аудит-лог в разделе «Функции».

{ "event": "device.create", "details": "...", "user": "admin", "ip": "10.0.0.5", "time": "2026-08-22T10:00:00.000Z" }

Опциональный секрет уходит в заголовок X-Netmonitor-Secret — используйте его на принимающей стороне для проверки подлинности запроса. Фильтр по конкретным типам событий — если ничего не выбрано, летят все.

Docs / Окна обслуживания

Окна обслуживания (Maintenance Windows)

Временная пауза алертов — мониторинг продолжается, уведомления не отправляются.

Назначение

Когда вы перезагружаете сервер, меняете оборудование или делаете резервное копирование — устройства временно уходят offline. Чтобы не получать ложные алерты, создайте окно обслуживания.

Мониторинг не останавливается. История пингов записывается, статусы обновляются. Подавляются только Telegram/Webhook уведомления.

Создание через UI

ПолеОписание

УстройстваВыбрать конкретные (Ctrl для мультивыбора)
Начало / КонецДата и время. Максимальная длительность — 30 дней
ПримечаниеОпционально — причина или ответственный

Статусы окон

АктивноОкно действует прямо сейчас. Алерты подавлены.
ЗапланированоНачало в будущем. Алерты работают в штатном режиме.
ЗавершеноАвтоматически удаляется через 7 дней.

Права

Создание и удаление — роли admin и operator. Просмотр — все авторизованные.

Docs / Мониторинг трафика

Мониторинг трафика

Загрузка канала (rx/tx) по устройствам через SNMP и по интерфейсам MikroTik-роутеров.

Модуль выключен по умолчанию. Включите: Настройки → Функции → «Мониторинг трафика».

Два источника данных

ИсточникКак работаетНастройка
SNMP-устройствоОпрос ifInOctets/ifOutOctets (IF-MIB) по указанному индексу интерфейса, дельта между опросами → bpsКарточка устройства → SNMP → «Индекс интерфейса (для трафика)»
MikroTik-роутер/interface/print через RouterOS API — счётчики rx-byte/tx-byte по интерфейсу, та же дельта → bpsНастройки → Интеграции → подключение MikroTik → «Интерфейсы для мониторинга трафика»

Как узнать индекс SNMP-интерфейса

SNMP-walk по OID 1.3.6.1.2.1.2.2.1.2 (ifDescr) вернёт список интерфейсов с их индексами:

snmpwalk -v2c -c public 192.168.1.1 1.3.6.1.2.1.2.2.1.2
IF-MIB::ifDescr.1 = STRING: ether1
IF-MIB::ifDescr.2 = STRING: ether2
IF-MIB::ifDescr.3 = STRING: wlan1

Число после точки (.1, .2, .3) — это и есть индекс интерфейса, который нужно указать в карточке устройства.

Опрос и хранение

ПараметрЗначение
Интервал опроса30 секунд (отдельный от ping-планировщика тик)
Первая точкаНе сохраняется — нужна как база для расчёта дельты на следующем опросе
Защита от переполнения счётчикаЕсли новое значение меньше предыдущего (32-битный wrap ~4.3ГБ) — используется как абсолютная дельта
ХранениеСырые точки 7 дней → агрегация в 10-минутные средние → удаление старше 30 дней
⚠ Это не замена Prometheus/Grafana для долгосрочных трендов трафика — встроенное хранилище рассчитано на недели, не на месяцы. Для долгой истории используйте /metrics endpoint с внешним time-series хранилищем.

Просмотр

Вкладка Трафик в основной навигации (появляется после включения модуля) — таблица текущих значений rx/tx по всем настроенным источникам, обновляется каждые 30 секунд через SSE. Клик на «📈 График» открывает график за 1ч/24ч/7д.

Docs / Агент (CPU/RAM/disk)

Агент

Лёгкий скрипт на самой машине шлёт метрики CPU/RAM/disk на NetMonitor. Ping видит только «жив/мёртв» — агент даёт заглянуть внутрь.

Как работает

Python-скрипт (только stdlib, без сторонних пакетов) собирает метрики раз в минуту и отправляет их POST-запросом с токеном устройства в заголовке Authorization: Bearer <токен>. Токен привязан к одному конкретному устройству — не даёт доступа к остальному API.

Установка

  1. Карточка устройства → детальная страница → карточка «Агент» → «Показать / сгенерировать токен» — скопируйте его (показывается один раз)
  2. Скачайте папку agent/ из репозитория на целевую машину
  3. Запустите установочный скрипт под свою ОС (ниже)

Linux (systemd)

sudo bash install-linux.sh --server https://netmonitor.local:9221 --token <ТОКЕН>

Windows (Планировщик заданий)

install-windows.bat https://netmonitor.local:9221 <ТОКЕН>

Вручную / проверка (любая ОС)

python3 netmonitor-agent.py --server https://netmonitor.local:9221 --token <ТОКЕН> --once

Флаг --once отправляет один отчёт и завершается — удобно для проверки перед установкой службы.

⚠ Самоподписанный сертификат: если NetMonitor использует автосгенерированный TLS-сертификат, добавьте --insecure к команде запуска — иначе агент откажется подключаться.

Собираемые метрики

МетрикаКак считается
CPU %Linux/Windows — точное чтение системных счётчиков (/proc/stat, GetSystemTimes). macOS — приближение через loadavg
RAM % / used / total/proc/meminfo (Linux), GlobalMemoryStatusEx (Windows), vm_stat (macOS)
Disk % / used / totalshutil.disk_usage() — путь настраивается через --disk-path (по умолчанию / или C:\)
UptimeВремя работы машины с последней загрузки
Hostname / OSИнформационно, для идентификации в случае нескольких агентов

Безопасность токена

  • Токен даёт право писать метрики только для одного устройства — не полный доступ к API
  • Показывается один раз при генерации — при повторном открытии карточки виден только префикс (a1b2c3d4••••••••)
  • «Перевыпустить» — старый токен мгновенно становится недействителен, нужно обновить конфиг агента на машине
  • «Отвязать» — удаляет токен полностью, история метрик сохраняется
  • Лимит частоты отправки — 20 запросов/мин на токен (см. раздел Rate Limiting)

Хранение и очистка

Метрики хранятся без downsampling (снимаются уже редко — раз в минуту). Автоочистка раз в час удаляет записи старше 30 дней.

Docs / SSE / Реалтайм

Server-Sent Events

Живые обновления статусов без перезагрузки страницы.

Эндпоинт

GET /api/events
Authorization: сессионный cookie (требует входа)

Как работает

После логина браузер подключается к /api/events через нативный EventSource. Сервер держит соединение открытым и пушит события при изменении данных. При разрыве — автоматическое переподключение через 5 сек.

События

eventКогдаdata
snapshotСразу при подключенииМассив текущих статусов: [{"id":"d-...","online":true,"lastChecked":...}]
statusПри смене online↔offline{"id":"d-...","online":false,"lastChecked":1234...}
incidentОткрытие/закрытие инцидента{"type":"open","deviceId":"...","deviceName":"..."}
pingКаждые 25 сек{"ts":1234...} — keepalive

Реакция фронтенда

СобытиеЧто обновляется
snapshotПолная перерисовка дашборда, таблиц, карты
statusТолько кольцо нужного узла на SVG-карте + строка в таблице мониторинга + счётчики дашборда
incidentToast-уведомление в браузере

Защита от перегрузки

SSE генерирует событие только при смене статуса (prev.online !== online), а не при каждом тике планировщика. При N устройствах с интервалом T — максимум N/T событий в секунду, обычно значительно меньше.

Docs / API / LDAP

API — LDAP / Active Directory

GET/api/ldap Текущие настройки LDAPadmin

Пароль сервисной учётной записи (bindPassword) маскируется как ••••••••, если задан.

Response 200

{ "enabled": false, "url": "", "bindDN": "", "bindPassword": "", "baseDN": "", "userFilter": "(sAMAccountName={{username}})", "defaultRole": "viewer", "roleMapping": [], "rejectUnauthorized": true }
POST/api/ldap Сохранить настройки LDAPadmin

roleMapping — список правил { group: "CN=...,DC=...", role: "admin"|"operator"|"viewer" }, проверяются сверху вниз, первое совпадение побеждает.

Request Body

{ "enabled": true, "url": "ldap://dc1.example.local:389", "bindDN": "CN=svc-netmonitor,...", "bindPassword": "...", "baseDN": "OU=Users,DC=example,DC=local", "roleMapping": [{ "group": "CN=NetAdmins,...", "role": "admin" }] }
POST/api/ldap/test Проверить соединение и Bind DNadmin

Пароль пользователя не проверяется — только bind сервисной учётной записью. Передайте { "useSaved": true } чтобы использовать уже сохранённые настройки без повторного ввода пароля.

Response 200

{ "ok": true, "message": "Соединение и Bind DN успешны." }
⚠ Вход через LDAP работает как дополнение к локальным учётным записям: если логин уже есть локально (например admin) — используется локальный пароль как обычно. Если логина нет локально и LDAP включён — выполняется поиск и проверка пароля в каталоге; при успехе учётная запись создаётся автоматически с ролью по группам. Пароль LDAP-пользователей нигде не хранится в NetMonitor.

Параметр range по умолчанию 24h. Ответ уже приведён к ≤200 точкам (downsampling на сервере) — готов для прямого построения графика.

API — Agent

POST/api/agent/report Приём метрик от агентаtoken

Авторизация не через сессию — через заголовок Authorization: Bearer <токен_устройства>. Публичный эндпоинт (без cookie), но требует валидный токен.

Body

{
  "cpu_pct": 12.3, "ram_pct": 45.1, "ram_used_mb": 3840, "ram_total_mb": 8192,
  "disk_pct": 67.8, "disk_used_gb": 135.6, "disk_total_gb": 200.0,
  "uptime_sec": 432000, "hostname": "server-01", "os": "Linux 6.8.0"
}

Все поля опциональны — сервер сохранит что есть, отсутствующие останутся null.

Response 200

{ "ok": true }

Response 401

{ "error": "invalid_token" }

Response 429

{ "error": "rate_limited", "message": "Слишком много отчётов от агента..." }
Лимит — 20 запросов/мин на токен (не на IP) — несколько агентов за одним NAT не мешают друг другу.
