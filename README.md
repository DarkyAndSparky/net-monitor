# NetMonitor — мини веб-сайт мониторинга локальной сети

Дешборд, реестр устройств и SVG-карта сети для локальной сети (MikroTik и не только).

## Запуск

Нужен установленный **Node.js v18+** (нужен встроенный `fetch` — используется для отправки алертов
в Telegram/Webhook). Скачать: https://nodejs.org/

### Самый простой способ — один скрипт

**Windows:** дважды кликните `start.bat` (при первом запуске он сам поставит зависимости).

**Linux/macOS:**
```bash
cd network-monitor
./start.sh
```
Если файл не запускается («Permission denied»), один раз выполните `chmod +x start.sh install.sh`.

`start.bat` / `start.sh` при каждом запуске сами проверяют, установлены ли зависимости
(папка `node_modules`) и не менялся ли `package.json` — если нужно, сначала выполняют `npm install`,
а затем запускают сервер. Отдельно ставить зависимости не обязательно, но при желании можно
сделать это заранее через `install.bat` / `./install.sh`.

### Вручную (через npm)

```bash
cd network-monitor
npm install
npm start
```

### После запуска

Сайт будет доступен:
- на этой же машине: `http://localhost:9222`
- с любого устройства в локальной сети: `http://<IP-этой-машины>:9222`

Порт можно поменять переменной окружения `PORT`, например: `PORT=8080 ./start.sh` (Linux/macOS)
или `set PORT=8080 && start.bat` (Windows).

### Если `npm install` спотыкается на пакете `ssh2` (нужен для интеграции с Cisco)

На некоторых системах (особенно старые Windows без Visual Studio Build Tools) `ssh2` может
попытаться собрать нативный ускоритель и упасть. Это не критично — сам пакет по-прежнему
установится и будет работать (просто без ускорения), просто увидите предупреждение в логе
`npm install`, а не ошибку установки в целом. Если весь `npm install` всё же падает из-за этого —
самый простой путь: установите Node.js LTS с сайта nodejs.org (там уже есть нужные компоненты)
либо на Windows поставьте `windows-build-tools`/Visual Studio Build Tools.

## HTTPS

Сервер умеет сам работать по HTTPS — реверс-прокси не нужен. **`start.sh` / `start.bat` теперь сами
генерируют самоподписанный сертификат при первом запуске**, если его ещё нет и в системе есть
`openssl` — ничего вручную делать не нужно, сервер сразу поднимется на HTTPS.

По умолчанию автосертификат выписывается на `localhost` / `127.0.0.1`. Если заходите не через
`localhost`, а по IP из локальной сети — сгенерируйте сертификат под этот IP явно (один раз),
иначе браузер помимо «сертификату не доверяют» будет ругаться ещё и на несовпадение имени хоста:

```bash
./make-cert.sh 192.168.1.50   # Linux/macOS
```
```bat
make-cert.bat 192.168.1.50    :: Windows (нужен openssl в PATH — есть в Git for Windows)
```

Сервер сам обнаруживает `data/certs/cert.pem` + `key.pem` при старте, переключается на HTTPS и
автоматически включает `secure`-флаг у cookie сессии. Браузер один раз покажет предупреждение
«сертификату не доверяют» — это нормально для самоподписанного сертификата в закрытой сети,
просто подтвердите переход.

**Если у вас есть настоящий сертификат** (например, от внутреннего CA компании или Let's Encrypt
для домена, если сайт смотрит наружу) — просто положите его файлы как `data/certs/cert.pem` и
`data/certs/key.pem`, либо укажите свои пути переменными окружения `TLS_CERT_FILE` / `TLS_KEY_FILE`.

**Дополнительно:** редирект с обычного `http://` на `https://` включён **по умолчанию на 80-м порту**
(это стандартный порт, на который браузер стучится, когда вы просто пишете `http://<IP>` без порта
в адресе) — специально настраивать ничего не нужно. Поменять порт редиректа или выключить его:
`HTTP_REDIRECT_PORT=8080 npm start` (или `0`, чтобы выключить совсем). На Linux/macOS порты <1024
требуют повышенных прав — если редирект не поднимется (например, сервис запущен не от root), в логе
будет понятное предупреждение, а сам сайт по HTTPS продолжит работать как обычно.

**Важно про адрес в браузере:** `https://<IP>:9222` (порт HTTPS) откроется всегда напрямую.
А вот `http://<IP>:9222` (тот же номер порта, но по HTTP) работать не будет и не может — порт 9222
теперь понимает только TLS-трафик, обычный HTTP на нём вызовет ошибку в браузере вроде
«не удаётся обеспечить безопасное соединение». Редирект работает именно с 80-го порта, то есть
на просто `http://<IP>` (без указания порта).

Если openssl не установлен — сервер как и раньше работает по обычному HTTP (для доверенной LAN
этого обычно достаточно).

Чтобы узнать IP машины, на которой запущен сервер: `ip a` (Linux) или `ipconfig` (Windows).

## Автозапуск (чтобы работало постоянно)

Linux (systemd) — пример unit-файла `/etc/systemd/system/netmonitor.service`:
```ini
[Unit]
Description=NetMonitor
After=network.target

[Service]
WorkingDirectory=/path/to/network-monitor
ExecStart=/usr/bin/node server.js
Restart=always
User=youruser

[Install]
WantedBy=multi-user.target
```
Затем: `systemctl enable --now netmonitor`

Либо проще — через `pm2`:
```bash
npm install -g pm2
pm2 start server.js --name netmonitor
pm2 save
pm2 startup
```

## Что внутри

- **Авторизация и роли** — сайт закрыт логином/паролем, две роли: **администратор** (полный доступ)
  и **только просмотр** (видит дешборд/устройства/карту/мониторинг, но не может ничего менять —
  без добавления/редактирования устройств, без настроек, без обнаружения сети). Пользователи по
  умолчанию: `admin` / `admin`, роль администратора. **Обязательно смените пароль** после первого
  входа. Новых пользователей и их роли добавляет администратор в «Настройках» → «Пользователи».
- **Дешборд** — доступность (пинг) ключевых устройств + мини-график (спарклайн) истории
  и % аптайма за 24 часа / 7 дней + счётчики устройств по категориям.
- **Алерты** — раздел «Настройки» → «Алерты»: включаете, задаёте порог (после скольких провалов
  проверки подряд слать уведомление — 1/2/3/5) и интервал повторной отправки, пока устройство не
  восстановится (не повторять / каждые 15 мин / 30 мин / час / 3 часа), плюс отдельно можно включить
  уведомление о восстановлении. Каналы — **Telegram-бот** (Bot Token + Chat ID) и/или **произвольный
  Webhook** (POST JSON на ваш URL — годится для интеграции с любой системой). Есть кнопка «Отправить
  тестовое». Оповещения по конкретному устройству можно отключить отдельно — галочка «Уведомления»
  в карточке устройства или переключатель в столбце «Алерты» на вкладке «Мониторинг» (сам пинг при
  этом продолжится, просто без уведомлений).
- **Интеграции: MikroTik / UniFi / Cisco** — «Настройки» → «Интеграции»: единая форма «Добавить
  подключение» с выбором типа (поля меняются под выбранный тип), и единый список всех подключений
  с кнопкой «Импортировать» у каждого.
  - **MikroTik** (RouterOS API) — как и раньше: DHCP-lease, ARP, MNDP-соседи, автотопология.
    Можно добавить сколько угодно роутеров, у каждого — своя кнопка «Импортировать», плюс общая
    «Импортировать со всех MikroTik разом».
  - **UniFi** (Ubiquiti) — логин/пароль контроллера; поддерживаются и UniFi OS консоли
    (UDM/UDM Pro/Cloud Key Gen2+ — отметьте галочку «Это UniFi OS консоль»), и классические
    software-контроллеры/Cloud Key Gen1. Импортируется и инфраструктура (точки доступа, свитчи,
    шлюзы — категория «Сетевое оборудование»), и подключённые клиенты. Самоподписанный сертификат
    контроллера принимается автоматически (ожидаемо для локальной сети).
  - **Cisco** — по SSH, выполняется `show ip arp`, MAC-адреса приводятся из формата Cisco
    (`aabb.ccdd.eeff`) к привычному (`AA:BB:CC:DD:EE:FF`). Нужен пользователь с правом
    просмотра (privilege level 15 надёжнее всего) и включённый SSH v2.
    ⚠️ Эта интеграция не проверялась на реальном оборудовании Cisco — реализована по
    документированному формату вывода команд, но если у вас нестандартная конфигурация/версия
    IOS с другим форматом вывода, парсинг ARP может не сработать — дайте знать, поправим.
- **Обнаружение сети и топология** — вкладка «Обнаружение»:
  - *Скан подсети* — ping-sweep указанного диапазона (например `192.168.1.0/24`, до 256 адресов),
    показывает, какие IP отвечают и есть ли они уже в реестре; можно добавить отмеченные одним кликом.
  - *ARP-таблица MikroTik* — тянет `/ip/arp/print` с выбранного роутера: IP + MAC + порт роутера,
    на который зашита эта запись.
  - *Соседи (MNDP)* — тянет `/ip/neighbor/print`: устройства MikroTik/RouterOS, которых роутер видит
    напрямую (имя, платформа, порт).
  - *«Построить топологию»* — берёт данные ARP + MNDP с выбранного роутера и рисует на карте
    **реальные связи** «роутер → устройство» с подписью порта, вместо условной «звезды от ядра».
    Устройства, которых ещё нет в реестре, создаются автоматически. Повторный запуск для того же
    роутера полностью пересчитывает его связи (старые заменяются новыми).
  - Для устройств без построенной связи карта по-прежнему рисует пунктирную линию к ядру сети —
    ничего не «теряется», просто выглядит как «неизвестно, куда физически подключено».
- **Поиск по карте** — поле «Найти устройство» в тулбаре карты: ищет по имени/IP/MAC, карта сама
  панорамируется к найденному узлу и подсвечивает его пульсирующим кольцом.
- **Иконки по типу устройства** — расширенный набор (роутер, свитч, точка доступа, файрвол, камера,
  NVR, NAS, сервер, ИБП, принтер, ноутбук, IP-телефон, ТВ-панель и т.д.); если тип не распознан —
  используется иконка по умолчанию для категории вместо одной точки на все случаи.
- **Древовидная схема** — кнопка «🌳 Дерево» на карте: переключает со свободной раскладки на
  автоматическую иерархию по связям (и автообнаруженным, и проведённым вручную). Родитель связи —
  выше, все его «дети» — ровным рядом ниже, по уровням. Есть переключатель ориентации
  (⇅ вертикально / ⇄ горизонтально — удобно для широких «плоских» деревьев с одним свитчом
  и множеством конечных устройств). Несколько корней (несколько роутеров) — несколько отдельных
  деревьев рядом. Устройства без единой связи не теряются — идут отдельным рядом в конце. В этом
  режиме узлы не перетаскиваются (позиции всегда пересчитываются), но связи по-прежнему можно
  редактировать кнопкой «Редактировать связи» — это и есть способ поменять структуру дерева.
- **Ручное редактирование связей на карте** — кнопка «🔗 Редактировать связи» (только у администратора):
  кликаете первое устройство, затем второе — появляется линия, можно подписать (например, «через
  свитч в шкафу» или номер порта). Клик по существующей линии в этом режиме — удаление. Актуально,
  когда свитчи неуправляемые и LLDP/MNDP от них получить нельзя — автотопология тут бессильна,
  связи проводятся руками поверх (или вместо) автообнаруженных.
- **Правила подсетей** — кнопка «☁ Правила подсетей»: задаёте диапазон вида `10.7.7.0/24` → «Wi-Fi
  клиенты» со своим цветом, и карта сама обводит все устройства с IP из этого диапазона полупрозрачным
  «облаком» с подписью. Удобно при сегментации по подсетям/VLAN, когда сотня устройств технически
  висит на одном порту одного свитча и рисовать реальные линии смысла нет — но зато сразу видно,
  где Wi-Fi, где проводные, где видеонаблюдение.
- **Зум и панорамирование карты** — колесо мыши (зум к курсору), кнопки +/−, кнопка «⛶ Уместить всё»
  автоматически подбирает масштаб под все устройства на карте. Полезно, когда точек много и всё
  превращается в кашу на стандартном масштабе.
- **Валидация IP/MAC в форме устройства** — до отправки на сервер проверяется формат; при этом
  поле «IP» по-прежнему принимает и hostname (сервер умеет пинговать DNS-имена), блокируются
  только явно некорректные значения (спецсимволы, октет больше 255, неверный формат MAC).
- **Дублирование устройства** — кнопка «⧉» рядом с редактированием: открывает форму добавления,
  предзаполненную данными исходного устройства (кроме IP/MAC — их вводите свои).
- **Версия приложения** видна в подвале бокового меню (берётся из `package.json`, отдаётся через
  `/api/health`).
- **База производителей (OUI)** — определение производителя устройства по MAC-адресу (реестр
  IEEE, ~30 тыс. записей). Скачивается автоматически при старте сервера, если данных ещё нет
  или они старше 30 дней; при неудаче (например, нет интернета — сайт же для локальной сети)
  тихо продолжает работать со старым кэшем. Статус и ручное обновление — «Настройки» →
  «Импорт/Экспорт» → «База производителей». Производитель показывается мелким текстом под
  MAC-адресом в таблице/карточках устройств.
- **Тип устройства — выпадашка с иконками** вместо свободного текста (Router/Switch/Access
  Point/Firewall/IP Camera/Server/NAS/UPS/PC/Printer и т.д.), с опцией «Другое» для нестандартных
  типов. Иконка отображается и в таблице, и в карточках, и на карте.
- **Пагинация в реестре устройств** — 25/50/100 на странице или «показать все», листание
  вперёд/назад. Выделение чекбоксами (для массовых операций) сохраняется при переходе между
  страницами — привязано к id устройства, а не к позиции на экране.
- **Массовые операции с устройствами** — на вкладке «Устройства» отмечаете чекбоксами несколько
  штук (или «выбрать все»), появляется панель: сменить категорию, включить/выключить мониторинг,
  удалить выбранные разом. Изменяются только безопасные поля (категория, мониторинг, алерты,
  интервал, расположение) — координаты на карте и id трогать нельзя, даже если что-то пойдёт не так.
- **Экспорт полного списка устройств в CSV** — кнопка «⬇ Экспорт CSV» на вкладке «Устройства»,
  сразу открывается в Excel (со всеми полями: имя, IP, MAC, расположение, тип, категория,
  комментарий, статус мониторинга).
- **Категории устройств — редактируемые** — «Настройки» → «Категории устройств»: добавление,
  переименование, смена цвета прямо из интерфейса (раньше это можно было поменять только вручную
  в `server.js`). Нельзя удалить категорию, пока на неё ссылается хотя бы одно устройство — сначала
  перенесите их в другую категорию.
- **Esc закрывает открытое модальное окно** (карточка устройства, подпись связи, правила подсетей).
- **`/api/health`** — эндпоинт без авторизации для внешнего мониторинга самого NetMonitor (например,
  Uptime Kuma или другим сторожевым сервисом): `GET /api/health` → `{"status":"ok","uptimeSec":...}`.
- **Резервная копия** — «Настройки» → «Резервная копия»: одной кнопкой скачиваете полный снимок
  всех данных (устройства, пользователи, настройки, история, топология, инциденты, аудит-лог)
  в одном JSON-файле; там же — восстановление из такого файла (с явным предупреждением,
  восстановление полностью заменяет текущие данные).
- **Сортировка таблицы устройств** — клик по заголовку столбца (Название/IP/MAC/Расположение/
  Тип/Категория), повторный клик — обратный порядок.
- **Копирование IP/MAC** — клик по значению в таблице или карточке устройства копирует его
  в буфер обмена (учтите: работает только по HTTPS или на localhost — так требует сам браузер).
- **Дополнительные модули (каждый включается отдельно)** — раздел «Настройки» → «Функции»,
  по умолчанию всё выключено, чтобы не грузить сеть/сервер лишним опросом:
  - **SNMP-мониторинг** — аптайм и загрузка CPU по SNMP (community/порт задаются в карточке
    устройства). Для MikroTik сразу работает предустановленный OID загрузки CPU.
  - **Проверка TCP-портов/сервисов** — не просто ping, а что конкретный порт отвечает
    (например 554 у камеры, 3389 у сервера) — список портов через запятую в карточке устройства.
  - **История инцидентов + эскалация** — вкладка «Инциденты»: журнал даунтаймов (когда и на сколько
    устройство падало) с MTTR за 7 дней, плюс в «Настройках» → «Алерты» появляется доп. блок
    эскалации — если проблема не решается дольше заданного времени, шлётся отдельное уведомление
    (можно в отдельный Telegram-чат, например дежурному инженеру).
  - **Аудит-лог** — раздел «Настройки» → «Аудит-лог»: кто и когда добавил/изменил/удалил устройство,
    поменял настройки или пользователя.
- **Импорт устройств из CSV** — «Настройки» → «Импорт устройств из CSV»: вставляете текст с колонками
  `name,ip,mac,location,type,category,comment` (обязательны только `name` и `ip`), дубли по IP/MAC
  пропускаются автоматически.
- **Отчёт по аптайму** — «Настройки» → «Отчёты»: скачивание CSV со всеми устройствами и их
  аптаймом за 24ч/7д, открывается прямо в Excel/Google Таблицах.
- **Настройки — разбиты на подвкладки** — раньше «Настройки» были одной длинной страницей,
  теперь это пилюли-переключатели: Внешний вид / Алерты / MikroTik / Категории / Пользователи /
  Функции / Импорт-Экспорт / Аудит-лог / Профиль / О системе.
- **Тёмная/светлая тема** — переключатель в «Настройки» → «Внешний вид», запоминается в браузере
  каждого пользователя отдельно (не влияет на других). Админ задаёт тему по умолчанию для тех,
  кто ещё не выбрал свою.
- **Брендинг** — админ может поменять название приложения (отображается в шапке, на экране входа,
  в заголовке вкладки браузера), акцентный цвет (красит кнопки/ссылки/выделения по всему
  интерфейсу) и загрузить свой логотип (SVG/PNG/JPG, до 1 МБ — SVG проверяется на `<script>`
  и обработчики событий, такие файлы отклоняются). Раздел «О системе» — версия и ссылка на
  исходники.
- **Мониторинг (управляемый список)** — отдельная вкладка «Мониторинг»: полный список устройств
  с переключателем «мониторить» у каждого и выбором интервала проверки (15с / 30с / 1мин / 5мин / 15мин).
  **Опрашиваются (пингуются) только те устройства, у которых мониторинг включён** — остальные просто
  хранятся в реестре, не создавая лишней сетевой нагрузки. Есть кнопки «Добавить все» / «Убрать все»
  и «Проверить сейчас» для мгновенной внеплановой проверки конкретного устройства.
  То же самое можно включить/выключить и прямо в форме добавления/редактирования устройства.
- **Устройства** — таблица и карточки, поля: название, IP, MAC, расположение, тип, категория, комментарий.
  Поиск и фильтр по категориям, добавление/редактирование/удаление.
- **Карта сети** — SVG-схема, узлы = устройства (иконка по типу, цвет по категории, обводка = статус пинга),
  можно перетаскивать мышью — позиция сохраняется на сервере.
- **Импорт из MikroTik** — раздел «Настройки» → указываете IP роутера, API-порт (8728 по умолчанию,
  или 8729 для api-ssl), логин/пароль → кнопка «Импортировать сейчас» подтягивает список
  `/ip/dhcp-server/lease` и создаёт/обновляет устройства (сопоставление по MAC/IP).
  **На MikroTik должен быть включён сервис `api`**: IP → Services → api (или api-ssl).

## Данные

Хранятся в JSON-файлах в папке `data/` на сервере (без внешней БД) —
поэтому все пользователи в сети видят одну и ту же карту и один и тот же список устройств:
- `devices.json` — устройства
- `users.json` — пользователи и роли (пароли хранятся хешированными, не в открытом виде)
- `settings.json` — список MikroTik-роутеров и настройки алертов (Telegram/Webhook)
- `history.json` — история пинга по каждому устройству (для графика аптайма)
- `topology.json` — связи устройств на карте: автообнаруженные (`manual: false`) и добавленные
  руками (`manual: true`) — хранятся вместе, автопостроение трогает только свои старые связи
  от того же роутера, ручные не трогает никогда

Категории задаются в `server.js` в функции `defaultCategories()` — можно
переименовать/добавить/убрать под свои нужды (например разделить видеонаблюдение
на "камеры" и "NVR", добавить "IoT" и т.д.).

## Проверка доступности (пинг) и история

- Опрашиваются только устройства из контролируемого списка мониторинга (вкладка «Мониторинг»), каждое —
  со своим интервалом. Планировщик на сервере проверяет раз в 5 секунд, кому из включённых устройств
  «пора» проверяться (то есть сама проверка сети — не чаще, чем задан интервал для конкретного устройства).
- Результат кэшируется и отдаётся во все интерфейсы (дешборд/таблица/карта) без повторного «живого» пинга
  на каждое открытие страницы — только реальные проверки по расписанию плюс кнопка «Проверить сейчас».
- Каждая выполненная проверка сохраняется в `history.json` (хранится примерно 7 дней) — на основе этой
  истории считается % аптайма и рисуется спарклайн на карточках ключевых устройств в дешборде.
- Устройства с выключенным мониторингом на карте показаны пунктирной обводкой, в таблице/дешборде —
  статусом «Не отслеживается».

## Безопасность — что сделано и что важно знать

Проведено два аудита по мере роста функциональности.

**Аудит №1 (базовая версия) — исправлено:**
- 🔴 **Command injection через поле IP** — раньше IP устройства подставлялся напрямую в shell-команду
  `ping`. Злоумышленник, который мог добавить/отредактировать устройство, мог вписать в поле IP
  что-то вроде `1.1.1.1; rm -rf /` и выполнить произвольные команды на сервере. Исправлено: адрес
  строго проверяется по маске (только буквы/цифры/точки/двоеточия/дефисы) и передаётся в `ping`
  без участия shell (`execFile`, а не `exec`).
- 🟠 Секрет сессии был захардкожен в коде → теперь генерируется случайно при первом запуске
  (`data/.session-secret`).
- 🟠 Не было защиты от подбора пароля → 5 неудачных попыток входа с одного IP = блокировка на 5 минут.
- 🟡 Cookie: явные `httpOnly`, `sameSite=lax`; лимит тела запроса; security-заголовки
  (`X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Strict-Transport-Security` на HTTPS).
- 🟡 Минимальная длина пароля увеличена с 4 до 8 символов.

**Аудит №2 (после добавления SNMP/бэкапов/CSV/discovery/массовых операций/ролей) — исправлено:**
- 🔴 **Неограниченное слияние `req.body` в устройство при `PUT /api/devices/:id`** —
  `{ ...existing, ...req.body }` позволяло записать в устройство любое поле, не только
  задокументированные (в отличие от остальных эндпоинтов, где всегда используется явный allowlist
  разрешённых полей). Заодно этот же PUT не валидировал `checkInterval` (в отличие от POST).
  Исправлено: явный список разрешённых полей + валидация `checkInterval`/`x`/`y`, как и везде
  в остальном коде.
- 🟠 **Роль/доступ пользователя не перепроверялись на каждый запрос** — при логине роль
  ('admin'/'viewer') кэшировалась в сессии и больше не сверялась с `users.json`. Значит, если
  админ удалял пользователя или понижал его до viewer, у уже открытой сессии этого человека права
  сохранялись вплоть до 12 часов (пока сессия не истечёт сама) — «отозвать доступ» на практике
  не срабатывало мгновенно. Исправлено: `requireAuth`/`requireAdmin` теперь на каждый запрос
  проверяют, что пользователь всё ещё существует, и пересчитывают его текущую роль из `users.json`.
- 🟠 **CSV/Formula injection в экспортах** (список устройств и отчёт по аптайму) — название,
  комментарий, расположение устройства — это свободный текст, который вводит любой admin (или он
  приходит из CSV-импорта). Если такое значение начиналось с `=`, `+`, `-` или `@` (например
  `=HYPERLINK(...)` или DDE-пейлоад вида `=cmd|' /C calc'!A0`), Excel при открытии экспортированного
  файла мог попытаться исполнить это как формулу — классический класс уязвимостей CSV injection.
  Исправлено по рекомендации OWASP: такие значения при экспорте в CSV префиксуются одинарной
  кавычкой, что превращает их обратно в обычный текст.
- 🟡 **Цвет категории/правила подсети и id категории не валидировались** — принимались от клиента
  как есть и подставлялись в `style="..."`/HTML-атрибуты на фронтенде без экранирования. Теоретически
  позволяло сохранить значение вроде `red"><img src=x onerror=...>` и получить hidden XSS, который
  сработает у любого другого пользователя (включая другого админа), открывшего дешборд/карту/список
  устройств — то есть stored XSS между пользователями системы, а не просто «атака на самого себя».
  Исправлено: сервер валидирует цвет строгим форматом `#RRGGBB` и id категории — безопасным набором
  символов; плюс на фронтенде теперь везде явно экранируются `name`/`color`/`id` категорий и правил
  подсетей при вставке в HTML/SVG (defense in depth — даже если где-то в будущем валидация на
  сервере будет случайно ослаблена, фронтенд всё равно не даст этому превратиться в XSS).
- SNMP и проверка TCP-портов проверены отдельно — обе фичи работают через сокеты (`net-snmp`,
  `net.Socket`), а не через shell, поэтому не создают новых векторов command injection.

**Осталось на вашей стороне:**
- Обязательно смените пароль `admin` сразу после первого запуска.
- Пароли MikroTik и Telegram Bot Token хранятся в `data/settings.json` **в открытом виде** —
  это сделано намеренно просто (без внешней БД/шифрования), поэтому: ограничьте права на файл
  (`chmod 600 data/settings.json`) и не публикуйте папку `data/` никуда. По возможности заведите
  на MikroTik отдельного read-only пользователя для API вместо полного admin.
- По умолчанию (без сертификата) сайт работает по обычному HTTP — трафик (включая пароль при
  входе) идёт открытым текстом. Для доверенной локальной сети это обычно приемлемо; если сеть
  не полностью доверенная (общий Wi-Fi, гостевой VLAN и т.п.) — включите встроенный HTTPS
  (см. раздел «HTTPS» выше, это `./make-cert.sh` + перезапуск) и ограничьте доступ файрволом
  до нужной подсети.
- Роли есть («администратор» / «только просмотр»), но нет более тонкого разграничения (например,
  «может тыкать чекбоксы мониторинга, но не может удалять устройства») — если появится нужда
  в промежуточных ролях, это отдельная доработка.
- JSON-файлы вместо настоящей БД — при одновременной записи нескольких процессов в теории возможна
  гонка (race condition), хотя для одного Node-процесса (как здесь) это не проблема. При заметном
  росте числа устройств стоит подумать о переезде на SQLite — это отдельная задача, сознательно
  не смешанная с остальными доработками.

## Исправленные баги

- **Кнопка «Добавить» в результатах скана/ARP не срабатывала** (вкладка «Обнаружение»). Причина:
  единственное место в коде, где обработчик клика собирался как `onclick='...'` с `JSON.stringify(...)`
  прямо внутри HTML-атрибута — хрупкий паттерн, отличавшийся от остального кода (везде рядом
  используется надёжный `data-idx` + `addEventListener`). Переписано на тот же надёжный паттерн.
  Заодно усилена генерация id устройств/связей: было `Date.now() + random`, стало
  `crypto.randomUUID()` — раньше при частых почти одновременных запросах теоретически была
  возможна коллизия id.
- **Подключение к UniFi по умолчанию использовало неверный порт для классических контроллеров** —
  порт 443 по умолчанию корректен только для UniFi OS консолей (UDM/UDM Pro/Cloud Key Gen2+);
  классический software-контроллер (или Cloud Key Gen1) слушает на 8443. Форма теперь сама
  подставляет правильный порт по умолчанию в зависимости от галочки «Это UniFi OS консоль»,
  плюс сообщения об ошибке подключения стали подробнее (код ответа + фрагмент тела ответа сервера).
- **Парсер OUI-базы производителей неверно разбирал строки без кавычек** — для организаций без
  запятой в названии регулярка захватывала не только название, но и весь остаток строки (включая
  адрес). Переписано на построчный разбор без регулярки для этой части.


## Возможные доработки

- LLDP/CDP-соседи для не-MikroTik свитчей — сейчас топология строится только по данным MikroTik
  (ARP + MNDP), поэтому «не видит» порты обычных неуправляемых свитчей за пределами роутера.
- Мультихоп-топология (устройство за свитчём за свитчём) — сейчас связь всегда «роутер → устройство»,
  даже если физически между ними есть промежуточный свитч.
- Уведомления (Telegram/email) при падении ключевого устройства — уже реализовано ✅ (см. «Алерты»).
- Роли пользователей (только просмотр / администратор) — уже реализовано ✅.
- Несколько слоёв/этажей карты с собственным фоном-планом здания.
